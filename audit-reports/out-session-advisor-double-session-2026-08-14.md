# Audit + План: паттерн «адвизор / двойная сессия» для dev-pomogator

**Дата:** 2026-08-14 · **Репозиторий:** dev-pomogator · **Статус:** отчёт + план (постройка после подтверждения)

## 1. Задача (как сформулировал владелец)

> «Я вариант адвизора. Сейчас когда кладе код вызывает сабагента, он типа засыпает: не
> смотрит как агент мыслит/что делает. Надо чтоб главный агент прям смотрел и реагировал
> как адвизор — стопал, подсказывал, как стоковый Anthropic Advisor, который вмешивается
> в сессию. Может, всегда двойную сессию клауде кода запускать по умолчанию — вместо
> opencode + claude code, две клауде кода: анализ и отчёт сперва.»

Отсюда извлечено:
- **Симптом:** адвизор слепнет, когда воркер вызывает субагента.
- **Хочу:** адвизор видит ход мысли субагента в реальном времени, перепроверяет на
  «пиздёж», стопает/поправляет, сам точечно правит харнесс воркера.
- **Идея по умолчанию:** двойная классическая сессия — воркер работает, адвизор следит
  за его транскриптом (включая субагентов) со своей точки зрения.

## 2. Что изучено

### 2.1 Живой эксперимент (октябрьская сессия)

Сессия `ses_00b9321adffezR4p0dDfROGH4H` (в opencode.db, проект `E:/repos/presentation-reels`)
была превращена владельцем в адвизора другой живой Claude Code сессии **`E:\repos\sales`,
`6126f730-d6c9-4eca-98ae-f858e110648f`** (задача — Ozon harness, 10 карточек, 403-дисциплина).

Что адвизор реально делал (все механики подтверждены файлами в `%TEMP%\opencode\`):

| Механика | Реализация | Работает? |
|---|---|---|
| Чтение транскрипта воркера | `tail_session.py` — хвост `~/.claude/projects/E--repos-sales/<id>.jsonl`, интервал 2-3 мин | ✅ |
| Чистка ANSI | `strip_ansi.py` | ✅ |
| Проверка фактов на «пиздёж» | сверка с `harness-coordinator.sqlite3` (таблица `run_external_blockers`), `capture-status.json`, манифестами, процессами | ✅ — дважды ловил ложь агента (фейковый «403» оказался 200 живьём) |
| Интерактивное управление чужой сессией | **pywinpty / ConPTY**-демон `pty_daemon.py`, протокол `claude-ctl.json` (`{action, prompt, wait}`) → `claude-rsp.json` (`{out, pid}`); запуск `claude --resume <id> --dangerously-skip-permissions` внутри PTY | ✅ |
| Подтверждение permission-диалогов | слать `1`/`2` в stdin; финально — перезапуск с флагом | ✅ с натяжкой |
| Промпты без поломки кавычек | промпт в файл → `send` в демон без shell-квотинга | ✅ |
| Скил-фиксация поведения | `.claude/skills/out-session-advisor/SKILL.md` + `.agents/skills/core/out-session-advisor/SKILL.md` + parity-реестр + роутинг (в presentation-reels) | ✅ |

Доменные истины, заработанные в той сессии и верные для «вмешательства»:
- `307 → 403 (…&__rr=1) → 200 (…&__rr=1&abt_att=1)` — штатная цепочка Ozon;
  **промежуточный 403 ≠ блокер**; блокер = финальный document ≥400 И `url === page.url()`.
- `__rr=1` — штатный параметр Ozon, не маркер блока.
- Бренд/артикул берётся со страницы после открытия (h1/«Бренд»/«Артикул»), **не из URL-slug**.
- `run_external_blockers.source` = `live` (стоп до `clear_run_external_blocker`) vs `archived` (диагностика, не морозит).
- Техсбой запуска («Chrome launcher PID did not expose owned browser child»,
  «profile 'Default' is missing») ≠ 403 и ≠ результат Ozon.

### 2.2 Главная слепота (ratchet — ваш исходный симптом)

Claude Code пишет транскрипт **субагентов в отдельные файлы**:
```
~/.claude/projects/<proj>/<session>/subagents/agent-<hash>.jsonl
```
(подтверждено в `6126f730.../subagents/` — десятки `agent-*.jsonl`, у каждого свой
`user/assistant/attachment`-поток).

А адвизор в той сессии читал **только главный** `<session>.jsonl`. Поэтому, когда воркер
запускал Explore/Plan/Task-субагента, ход мысли уходил в side-файл, и адвизор «засыпал» —
не видел, что именно думает субагент. Это ровно жалоба «он не смотрит как агент мыслит».

**Вывод для плана:** чтобы «прям смотрел» — адвизор обязан хвостить **живые транскрипты
субагентов** (открытые `agent-*.jsonl` рядом с главным), а не только главный файл.

### 2.3 Провалы той сессии (против чего строить защиту)

1. **Сам останавливался** после ответа вместо продолжающегося мониторинга (владелец: «хуле встал», «ты засыпаешь») — есть копия симптома в самом адвизоре.
2. Permission-диалоги жались вручную до тех пор, пока не перезапустил с `--dangerously-skip-permissions` — нужно стартовать с ним сразу.
3. Управление одним воркером выполнялось вручную, не было «по умолчанию».
4. `pty_daemon.py`, `tail_session.py` и проч. живут в `%TEMP%\opencode\` — неверсионированы, не распространяются с плагином.

### 2.4 Существующее в dev-pomogator (не дублируем)

- `tools/advisor/` (untracked PoC): `advisor_stop.ts` (детерминированный Stop-hook: DONE_CLAIM/recurring/plan → совет через `systemMessage`) + `mcp-server.mjs` (model-driven: модель сама зовёт `mcp__dev-pomogator-advisor__advisor` без параметров, сервер читает транскрипт) + `transcript-packet.mjs` + `bench/`.
  **Отличие:** это **клиентский аналог стокового /advisor внутри одной сессии**; новый skill —
  **адвизор внешней сессии** (два процесса/две Claude Code).
- Отчёты: `audit-reports/advisor-poc-2026-08-14.md`, `audit-reports/advisor-model-driven-2026-08-14.md`.

## 3. Архитектура «двойной сессии»

```
[воркер]  claude --resume <work-session> --dangerously-skip-permissions   (или fresh)
   │        единый писатель своего JSONL: <work-dir>/<work-session>.jsonl
   │        субагенты пишут: <work-session>/subagents/agent-*.jsonl
   ▼
[адвизор]  отдельный процесс/сессия: читает ВСЕ открытые jsonl воркера по интервалу,
           сверяет факты с диском/БД, шлёт промпты через ConPTY-демон, стопает при грязи,
           сам точечно правит файлы харнесса, которых воркер сейчас не трогал.
```

Три режима использования:
- **A (по запросу):** в любой сессии (opencode/Codex/Claude) сказать «будь адвизором X» —
  skill раскручивает цикл.
- **B (лаунчер):** скрипт поднимает сразу две Claude Code сессии: воркер + адвизор,
  слинкованные через ctl/rsp и транскрипт.
- **C (встроенный воркер):** адвизор сам вызвался на роль, когда воркер стартует — для
  будущей автоматизации (вне данного скоупа).

Гарантии качества (из опыта 2.3):
- **Один писатель в один файл.** Редактируем только файлы, которые воркер НЕ трогал
  (по его последним Edit в транскрипте); в JSONL воркера не пишем никогда.
- **Не вставать.** Цикл мониторинга интервальный; саммари владельцу периодически.
- **Факты на диске > слова агента.** Каждое заявление — к файлу/БД/процессу.
- **ConPTY + `--dangerously-skip-permissions`** при автономке воркера.

### 4.2 Шаги

1. **Перенести скрипты** из `%TEMP%\opencode\` в `tools/out-session-advisor/`, параметризовать
   (сейчас в `pty_daemon.py` захардкожены `cwd="E:/repos/sales"`, `claude.exe`, path winpty).
2. **tail_session.py → хвостить субагентов**: рядом с главным jsonl открыты живые
   `subagents/agent-*.jsonl`; читать последние блоки каждого с временными штампами, чтобы
   видеть ход мысли субагента, пока он работает.
3. **SKILL.md** — описать воркфлоу цикла (снять состояние → диагноз → промпт → мониторинг →
   перепроверка → саммари → CONTINUE), принципы «не вставать / один писатель / факты на
   диске», доменные истины, протокол ctl/rsp, ConPTY запуск с `--dangerously-skip-permissions`.
4. **Зеркало** `.agents/skills/out-session-advisor/` + при необходимости запись в
   `tools/skill-health/mirror-contract.json` (режим `legacy`/`adapted`).
5. **Спека + BDD**: фикстура реального транскрипта с субагентами (см. `6126f730.../subagents/`),
   тесты на tail-видимость и на verify-claims; прогон через Docker-cucumber (правило
   `no-host-bdd-runs`).
6. **Лаунчер (режим B, опционально вторым заходом)** — `tools/session-pilot` уже умеет
   поднимать/резюмить сессии в worktree; скил может использовать его `/api/launch`, чтобы
   не заново писать терминал-клей.

### 4.3 Верификация плана

- Ручной live-прогон: воркер = свежая `claude` задача в тестовой папке, адвизор следит;
  проверить что субагентные ходы видны в tail-выводе, что промпт доходит через ctl/rsp,
  что факт-проверка ловит подставленную ложь.
- `npm run check:skill-health` (если skill-контроль включён в репо).

## 5. Риски / открытые вопросы

1. **Два процесса + один session-id**: если воркер уже жив в окне владельца, а адвизор
   захочет `claude --resume` того же id — конфликт писателей JSONL. Правило: сначала
   закрыть окно воркера, затем чей-то один управляет. (В эксперименте убивали старый процесс.)
2. **pywinpty под Python 3.14** на Windows — в эксперименте были мучения с установкой
   (`pip` в user-site, `import winpty`). Нужна надёжная схема установки/пути в скиле.
3. **Субагентные jsonl не всегда закрыты сразу** — tail должен брать незакрытые файлы
   (читать до последней строки, не ждать EOF).
4. **Стоимость**: постоянный опрос транскриптов + перепроверка — дешевле на
   локальном `/v1/messages` (meridian-model-call), чем гнать отдельную модель.
5. **Сфера**: лаунчер «двух клауде по умолчанию» — отдельная фича; сначала skill+скрипты.
