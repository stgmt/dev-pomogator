# Анализ: перекличка показывает «не прогонялось» для проверенных сценариев

> Статус: **только анализ + предложения** (по просьбе владельца — в спеки НЕ записано, чтобы взять в работу
> отдельно после ревью). Дата: 2026-06-29. Автор-сессия: BDD-миграция (fd1bcc98).

## 1. Симптом (простыми словами)

Я проверяю один набор сценариев точечно (например, только `devcontainer` или только `SPECGEN003`), он
**зелёный в Docker** — но перекличка (census-хук + `spec-status`) после этого показывает эти же сценарии
как «ещё не прогонялись» (`not_run` / `done-but-not-run`). То есть **проверка прошла, но в перекличке её не
видно**. Сейчас: `207 open, 190 ⏸ done-but-not-run`.

## 2. Как считается перекличка (механизм, с пруфами)

Один источник истины — канон `.dev-pomogator/.last-test-run.ndjson`:

- Канон ингестится в спек-граф как `ScenarioNode.lastResult` [ref:tools/spec-graph/coverage.ts:4-5].
- Сценарий, **отсутствующий** в последнем NDJSON → бакет `not_run` (а не «не покрыт») [ref:tools/spec-graph/coverage.ts:142-145].
- Перекличка: «все сценарии задачи passed» → confirmed; «≥1 not_run или нет сценария» → `done-but-not-run`
  [ref:tools/spec-graph/task-census.ts:121-124].

Кто **пишет** канон: `message:`-форматтер в `cucumber.json`. Только **полный** прогон
`bash scripts/docker-bdd.sh` (без фильтра) обновляет канон.

## 3. Почему фильтрованные/точечные прогоны не попадают в канон (это защита, не баг)

`scripts/run-bdd.mjs` намеренно уводит фильтрованный прогон в throwaway-файл, **не трогая канон**
[ref:scripts/run-bdd.mjs:6-19, 62-77]. Причина — «F2 footgun»: фильтрованный прогон, идущий через дефолт-
конфиг, **перетёр бы** канон частичным результатом, и всё вне фильтра прочиталось бы как `not_run`. Реальные
инциденты в комментариях кода: один диагностический прогон стёр полное покрытие (2026-06-18); `--dry-run`
залил канон 703 all-skipped событиями, `done-but-not-run` 43→234 (2026-06-20).

Три класса прогона и что они делают с каноном:

| Прогон | Канон | Перекличка видит результат? |
|--------|-------|------------------------------|
| Полный `docker-bdd.sh` (без аргументов) | перезаписывает целиком | да (все сценарии) |
| Фильтрованный `--name/--tags` | throwaway, канон цел | **нет** |
| Мой обход `-c cucumber.sx.json` + `format:['progress']` | **вообще не пишет** (нет message-форматтера) | **нет** |

То есть моя дисциплина «детерминированный обход гонки» (уникальный конфиг + `progress`) корректно НЕ портит
канон — но и НЕ записывает свой зелёный никуда, что перекличка читает.

## 4. Усилитель на общем дереве

Канон — общий файл, а параллельная claude-mem сессия **непрерывно** гоняет `docker-bdd`. Даже если бы я
сделал полный прогон (~70 мин) ради обновления канона, её прогоны тут же его перетрут. Поэтому «просто
прогони полный сьют» — не решение: результат недолговечен.

## 5. Почему это стало острым ИМЕННО сейчас

BDD-миграция этой сессии добавила ~13 наборов сценариев, каждый я валидировал **точечно** (иначе гонка
канона даёт «0 сценариев»). Все они зелёные, но ни один точечный прогон не попал в канон → перекличка
честно, но обманчиво, показывает их `not_run`. Чем больше точечной валидации (а это правильный режим на
общем дереве), тем больше ложного `not_run`.

## 6. Уже существующая, но неиспользуемая половина решения

`run-bdd.mjs` **уже архивирует КАЖДЫЙ прогон** (полный И фильтрованный) в `.dev-pomogator/.test-history/`
с полным payload + компактным индексом [ref:scripts/run-bdd.mjs:81-147]. То есть данные о точечных зелёных
**не теряются** — они лежат в истории. Но **перекличка/покрытие их не читают** (читают только канон). Это
ключ: половина инфраструктуры (запись истории) есть, не хватает второй половины (чтение-слияние).

Оговорки: (а) архив пропускает `-c`-прогоны (мой обход) [ref:scripts/run-bdd.mjs:88-93]; (б) `docker-bdd.sh`
гонит cucumber в контейнере напрямую, не через `run-bdd.mjs`, поэтому в Docker архив надо подключать
отдельно.

## 7. Варианты лучшего дизайна

### Вариант A — канон как ПОСЦЕНАРНОЕ слияние, а не перезапись файла (принципиальный)
Любой прогон (полный ИЛИ фильтрованный) **обновляет только свои сценарии** по `scenario id`, остальные
сохраняет. Тогда:
- F2-footgun исчезает сам (фильтрованный физически не может стереть чужое) → throwaway-обход больше не нужен;
- точечная валидация записывает свой зелёный → перекличка его видит.
- Нужна **посценарная метка времени** + окно свежести (старый pass не считать вечно зелёным — иначе
  спрячем регрессию). Это меняет семантику канона (снимок → накопление), что затрагивает `spec-verdict`,
  honesty-gate, перекличку — все читатели канона.

### Вариант B — перекличка читает СЛИЯНИЕ (канон + `.test-history`, посценарно most-recent)
Канон оставить снимком полного прогона; перекличку/покрытие научить дочитывать `.test-history` и брать по
каждому сценарию самый свежий результат. Плюс: переиспользует уже пишущуюся историю. Минусы: (а) надо
заставить `-c`-обход и docker-фильтр тоже писать message-ndjson в историю; (б) логика чтения усложняется
(слияние + свежесть). Источник истины раздваивается.

### Вариант C — лёгкий посценарный side-log «verified»
Любой валидирующий прогон дописывает `{scenario_id, result, ts, run_id}` в append-only лог; перекличка
читает канон + лог (most-recent по сценарию). Проще всего писать; перекличка сливает. По сути B, но
целевой компактный лог вместо чанков истории.

## 8. Рекомендация

**Вариант A** (посценарное слияние с метками времени) — самый чистый: одним ходом убивает И F2-footgun, И
ложный `not_run`-после-фильтра, и делает «полный прогон ~70 мин» необязательным. Свежесть закрывается
посценарным timestamp + окном (например, pass старше N дней или старше mtime файла сценария → деградирует
до `stale`, не `passed`). Если A слишком инвазивен для читателей канона — **Вариант B** как промежуточный
(данные уже есть в `.test-history`, дописать только слияние в `coverage.ts` + архив для `-c`/docker).

Анти-цель: НЕ «просто гонять полный сьют» — на общем дереве он недолговечен (§4) и стоит 70 мин.

## 9. Второй анализ: хвост юнит-тестов (что реально осталось от «ноль `*.test.ts`»)

При сверке «ноль `*.test.ts`» оказалось: чисто только в `tests/e2e` + `tests/unit` (главные E2E-твины —
их и мигрировали). Осталось вне миграции (это «~120-файловый хвост» из правила `bdd-only-tests`) — **84
файла**:

| Где | Кол-во | Что это |
|-----|--------|---------|
| `tools/**/__tests__/*.test.ts` | **63** | ко-локированные юнит-тесты инструментов |
| `.claude/skills/**/__tests__/*.test.ts` | 4 | юнит-тесты скилл-скриптов |
| `.specs/backlog/**/_artifact/tests/*.test.ts` | 14 | сгенерённые артефакты бэклог-спек |
| `*_test.py` / `*Tests.cs` | 3 | питон/C# (другие языки, тоже цель bdd-only) |

**Природа хвоста (выборка проверена):** это **чистые юнит-тесты** — `import { fn } from '../x.ts'` +
вызов + assert, **ноль `spawnSync`/`execSync`** (`coverage.test.ts`, `tools.test.ts`, `check.test.ts` — все
import-and-call). Это ДРУГОЙ класс, чем сквозные твины этой сессии (те гоняли реальные CLI/установщики
через spawn). По области:

| Область | Тестов |
|---------|--------|
| spec-graph | 18 |
| spec-mcp-server | 13 |
| spec-backlog | 8 |
| anchor-integrity | 6 |
| marksman-installer | 4 |
| остальные 11 областей | по 1-2 |

**Оценка мигрируемости:**
- **Мигрируемы тем же приёмом, что `spec-status`/`plan-validator`** (BDD-сценарий импортит ту же функцию
  in-process и проверяет реальный возврат — «drive real code» удовлетворён вызовом, не обязателен spawn).
  Это ~71 файл (63 tools + 4 skills + ~4 на др. языках по их раннерам).
- **Кандидаты НЕ мигрировать, а оценить отдельно — 14 `_artifact/tests`** под `.specs/backlog/`: это
  СГЕНЕРЁННЫЕ спекой тестовые артефакты-заготовки, не рукописные твины; для них «ретайр vitest» может
  значить «перегенерить под BDD-таргет» или «исключить из счётчика как scaffolding», а не ручная миграция.
- **Объём:** ~71 рукописных юнит-файла. Это НЕ один заход — отдельная волна, разбитая по областям
  (естественные пакеты: spec-graph 18 → одна спека, spec-mcp-server 13 → одна, и т.д.). Каждая область =
  один homeless-feature `PLUGINxxx_<area>.feature` + step-def, импортящий функции области.
- **Риск-нюанс:** многие из них — тесты САМОЙ инфраструктуры спек-графа/переклички (`coverage.test.ts`,
  `task-census.test.ts`, `ndjson-ingester.test.ts`). Их BDD-двойники будут гонять тот же код, что считает
  покрытие — то есть §7-фикс этой переклички и миграция этого хвоста пересекаются (чинить перекличку лучше
  ДО/вместе с миграцией её собственных тестов, иначе мигрируешь под движущуюся мишень).

Итого: хвост — реальный отдельный ярус, мигрируем, но это волна по областям, а не один заход; 14
backlog-артефактов — отдельный under-вопрос (генерёжка, не ручная миграция).
