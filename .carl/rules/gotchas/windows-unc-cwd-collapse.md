# Windows подменяет UNC-cwd на C:\Windows — состояние нельзя якорить к process.cwd()

Когда проект живёт на UNC-пути (`\\wsl.localhost\Ubuntu\root\...`), Windows **не может**
использовать его как рабочий каталог. `cmd.exe` печатает
«UNC paths are not supported. Defaulting to Windows directory» и уходит в `C:\Windows`.

**Node сам по себе UNC переваривает нормально** — `process.cwd()` вернёт UNC-путь честно.
Ломается любой **шелл-хоп через cmd.exe**: `exec`, `execSync`, `spawn({shell:true})`,
а также хуки, которые Claude Code запускает через шелл.

## Правило

- Состояние (ack-файлы, маркеры, логи, конфиги) якорить к `input.cwd` из stdin хука,
  затем `CLAUDE_PROJECT_DIR`, и только в последнюю очередь `process.cwd()`.
- **Запись и чтение обязаны использовать ОДИН И ТОТ ЖЕ якорь.** Асимметрия — худший вариант:
  писатель кладёт файл в одно место, читатель ищет в другом, и оба «работают».
- Если резолв попал в системный каталог — **падать громко**, а не писать молча.
- Не доверять `${CLAUDE_PROJECT_DIR}`: в headless-контекстах он приезжает **нераскрытым
  литералом** (непустая строка, поэтому `|| cwd` его не ловит). Проверять на `${`.

## Инцидент (2026-07-13)

`subagent-watchdog` читал ack через `input.cwd`, а писал через `process.cwd()`
(`--ack`, строка 535). Под UNC квитанции ушли в `C:\Windows\.dev-pomogator\`, хук их не видел
и **блокировал Stop 18 часов подряд**. Агент часами правил файлы состояния руками, приняв
дефект инструмента за потерянную работу. Доказано A/B-прогоном: один и тот же транскрипт,
одна и та же сборка — `cwd`=проект даёт `approve`, `cwd`=`C:\Windows` даёт `block`.

Тем же механизмом в репозиторий заехала папка `%windir%/Panther/UnattendGC/*.xml` (настоящие
логи установщика Windows), а в `~/.claude/projects/` появился проект `C--WINDOWS-system32`.

## Чеклист

- [ ] Пути состояния не берутся из голого `process.cwd()`
- [ ] Писатель и читатель используют один якорь
- [ ] Системный корень (`C:\Windows`) отвергается явно
- [ ] Значение с `${` не принимается как путь
