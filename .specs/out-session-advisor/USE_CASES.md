# Use Cases

# Часть A — Адвизор

## UC-1: Адвизор берёт управление живой воркер-сессией @feature2 @feature3

Владелец просит «будь адвизором сессии X» (например `6126f730...` в `E:\repos\sales`).

- Адвизор определяет session-id и путь `~/.claude/projects/<proj>/<sid>.jsonl` (+ открытые `subagents/agent-*.jsonl`).
- Проверяет, нет ли второго живого писателя в этот же JSONL (иначе single-writer нарушается).
- При необходимости останавливает старое окно и поднимает воркер в ConPTY с `--resume <sid> --dangerously-skip-permissions`.
- Запускает цикл: снять транскрипт → диагноз → промпт → мониторинг → саммари.
- Результат: адвизор управляет и перепроверяет воркер до закрытия задачи.

## UC-2: Адвизор видит субагентов воркера @feature1 @feature3

Воркер запускает Explore/Plan/Task-субагента; мысль субагента уходит в `subagents/agent-*.jsonl`.

- Адвизор хвостит главный jsonl И живой каталог `subagents/`.
- Появляющиеся/растущие `agent-*.jsonl` попадают в снапшоты с временным штампом.
- Если субагент долго «думает» (нет записей) — адвизор различает живой процесс и остановку.
- Результат: слепота на субагентов устранена.

## UC-3: Адвизор ловит ложный отчёт воркера на «пиздёж» @feature3

Воркер пишет «fresh live HTTP 403 на карточку N», приложение не запускалось.

- Адвизор берёт пути/claim из отчёта, запускает `verify_claims.ts`.
- Делает независимую live-проверку (та же карточка, тот же профиль/флаги).
- Сверяет с БД (`run_external_blockers`) — `source=live|archived`.
- Результат: вердикт CONFIRMED/GAP с доказательством; воркер получает СТОП-промпт при лжи.

## UC-4: Адвизор стопает и перезапускает воркер при техне/403-инциденте @feature2 @feature3

Воркер упал в цепочку 403 или техдефект запуска, и сам не может выйти.

- Адвизор снимает снапшот и читает `capture-status.json`/`document_response_chain`.
- Интерпретирует: промежуточный 403 (`307→403→200`) ≠ блокер; финальный ≥400 = блокер; «Chrome PID did not expose owned browser child» = техсбой.
- Пишет СТОП/новое задание воркеру или сам точечно правит файл харнесса, которого воркер не трогает.
- Результат: воркер продолжает по правильному пути, без авто-повторов 403.

## UC-5: Адвизор отдаёт саммари и продолжает мониторинг @feature4

После завершения шага воркера адвизор не «встаёт».

- Формирует саммари: что сделано, что правда (с путями), что осталось.
- Планирует следующий интервал и продолжает цикл до закрытия задачи или явного стопа владельца.
- Результат: постоянная включённость, без зависаний на долгих думающих ходах.

# Часть B — Параллельная безопасность

## UC-6: Две сессии в одном репо, коммит без захвата чужого @feature6

Сессия A пишет фичу X, сессия B пишет фичу Y в том же рабочем дереве.

- Сессия A вызывает «закоммить» с явными путями.
- Инструмент сверяет staged-пути со списком недавно изменённых другими сессиями.
- Если пересечение найдено — предупреждение/блокировка до подтверждения владельца.
- Результат: чужие файлы не улетают в чужой коммит.

## UC-7: Два процесса борются за лок, атомарность спасает @feature7

Два параллельных процесса одновременно хотят обновить одно состояние.

- Оба используют `writeFile(lock, pid, {flag:'wx'})`.
- Победил первый; второй получает EEXIST и ждёт/выходит.
- Stale-лок упавшей сессии переживает и пересоздаётся.
- Результат: состояние не коррумпируется, есть единый владелец.

## UC-8: Инвентаризация по нескольким репо @feature8

Владелец держит сессии в sales, presentation-reels, dev-pomogator.

- `parallel-session-inventory` сканирует процессы/сессии/ворктри.
- Каждый процесс отнесён к репо или `unknown`.
- Результат: карта активной параллельности, пригодная адвизору.

## UC-9: Адвизор определяет «кто пишет <файл>» @feature9

Адвизор хочет править файл, который, возможно, трогает воркер.

- Запрос «кто писал <path>» по транскриптам параллельных сессий.
- Ответ: сессии + время последнего Edit/Write + последний писатель.
- Если активный писатель найден — предупреждение о single-writer.
- Результат: адвизор не портит чужую работу.

## UC-10: Диагностика параллельности @feature10

Спор двух сессий за один файл.

- Вызывается сводка: активные сессии, локалы, писатели, вердикты `ok/dirty/conflict`.
- Причина каждого конфликта показана (путь, времена записи, владелец лока).
- Результат: владелец/адвизор видят причину, а не голый факт блокировки.

## UC-11: Edge — `git add -A` в дереве без транскриптов других сессий @feature6

Неизвестное дерево (нет чужих транскриптов).

- Гейт работает в Fail-open: предупреждает, не жёстко блокирует.
- Результат: нет лжеконфликтов в среде, где параллельности нет.
