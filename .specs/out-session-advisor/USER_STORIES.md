# Часть A — Адвизор

### User Story 1: Адвизор следит за ходом мысли субагентов воркера @feature1 (Priority: P1)

**Требование:** [FR-1](FR.md#fr-1-tail-главного-транскрипта-живых-subagents-снятие-слепоты)

As a владелец нескольких параллельных агентных сессий, I want адвизор-сессия видела рассуждения и действия субагентов воркера в реальном времени, чтобы адвизор не «засыпал», пока воркер гоняет субагентов, и мог вмешаться до того, как субагент навредит.

**Why:** Claude Code пишет мысль субагентов в отдельные `subagents/agent-*.jsonl`, а адвизор читает только главный `<session>.jsonl` — на время работы субагента он слепнет (симптом «засыпает», подтверждён в сессии `ses_00b9321...`).

**Independent Test:** BDD-сценарий `@feature1` — запустить фейковый субагент, который пишет в `subagents/agent-test.jsonl`, и убедиться в хвосте `tail_session.py` появились его шаги.

**Acceptance Scenarios:**

Given живой воркер-сессия с открытыми `subagents/agent-*.jsonl`
When адвизор снимает хвост транскрипта по интервалу
Then в выводе видны текстовые и tool-события каждого открытого субагентного файла с временным штампом

Given субагент завершил работу, файл `agent-*.jsonl` больше не растёт
When адвизор снимает следующий хвост
Then отдельный субагентный блок помечается как закрытый, без повторного дублирования старых строк

### User Story 2: Адвизор перепроверяет отчёты воркера на «пиздёж» по фактам на диске @feature3 (Priority: P1)

**Требование:** [FR-3](FR.md#fr-3-факт-проверка-отчётов-воркера-verifyclaims)

As a владелец автономной воркер-сессии, I want адвизор сверял каждое заявление воркера с файлами, БД и процессами, чтобы ложные отчёты (вроде фейкового «HTTP 403», когда карточка открывается 200) не принимались на веру и воркер не «крутил» один и тот же тупик.

**Why:** В эксперименте адвизор дважды доказал ложь воркера живой проверкой (та же карточка на том же профиле → HTTP 200), а «логика одного блокера навсегда» замораживала запуск — только сверка с диском отделяла правду от «пиздёжа».

**Independent Test:** BDD-сценарий `@feature3` — подсунуть воркер-отчёт с выдуманным claim про файл/БД, `verify_claims.ts` должен вернуть status `GAP` с файл:строка-иденттификатором.

**Acceptance Scenarios:**

Given отчёт воркера утверждает факт, который надо проверить
When адвизор запускает `verify_claims.ts`
Then вердикт содержит `CONFIRMED` c evidence-путями, либо `GAP` с точной причиной

Given воркер заявляет «live 403 на карточку N»
When адвизор делает live-проверку той же карточки
Then адвизор либо подтверждает 403 (финальный document ≥400), либо помечает заявление ложным с доказательством

### User Story 3: Адвизор управляет воркером интерактивно без permission-диалогов @feature2 (Priority: P1)

**Требование:** [FR-2](FR.md#fr-2-управление-воркером-stream-json-primary-conpty-fallback)

As a владелец автономной воркер-сессии, I want адвизор запускал и продолжал воркер через stream-json мост с `--dangerously-skip-permissions` и слал промпты через `send`/`send_nowait`, чтобы не приходилось вручную жать каждый permission-диалог и адвизор мог стопать/подсказывать без поломки кавычек.

**Why:** В эксперименте permission-диалоги жались вручную до перезапуска с флагом; shell-квотинг ломал многострочные промпты — фикс «промпт → `send`» снял проблему, а `--dangerously-skip-permissions` убрал диалоги. Live-тест stream-json (2026-08-15) подтвердил: вопросы приходят текстом в `result`, permission-отказы — как `tool_result is_error`.

**Independent Test:** Смоук: stream-json-запуск воркера с одной командой, `send` промпта, дождаться `result` (type=result) — ответ пришёл без `FileNotFoundError` и с session_id.

**Acceptance Scenarios:**

Given воркер запущен через stream-json с `claude --resume <id> --dangerously-skip-permissions`
When адвизор шлёт промпт (`send`)
Then в `result` получен ответ воркера, `session_id` присутствует

Given воркер задаёт вопрос владельцу текстом в `result`
When адвизор читает `result` и отвечает через `send`
Then вопрос-ответ продолжается без перехвата диалогов (вариант A)

Given многострочный промпт с кавычками/спецсимволами
When адвизор пишет его в файл и шлёт через ctl
Then промпт попадает в поле ввода воркера без искажения (UTF-8), submission — отдельным Enter

### User Story 4: Адвизор не «встаёт» — интервальный мониторинг и саммари @feature4 (Priority: P2)

**Требование:** [FR-4](FR.md#fr-4-цикл-мониторинга-не-встаёт-живость-процесса-интервальные-снапшоты)

As a владелец, I want адвизор CONTINUE и интервально докладывал о ходе воркера, чтобы сессия не замирала на долгих думающих ходах субагентов и я получал саммари без напоминаний.

**Why:** Владелец трижды ловил адвизора на «встал» после ответа; долгие xhigh-ходы (5–15 мин без записи в транскрипт) не значит остановку — нужно отличать «думает» от «умер» (проверка живого процесса).

**Independent Test:** BDD-сценарий `@feature4` — после каждого «чистого» шага не менее одного последующего шага мониторинга (проверка живости процесса) присутствует в ходе.

**Acceptance Scenarios:**

Given адвизор завершил обработку снапшота
When проходит интервал мониторинга (2–3 мин)
Then адвизор снимает новый снапшот/проверяет живость процесса и не оставляет ход без следующего действия

Given воркер в долгом думающем ходе без записей
When интервал истёк, но процесс жив
Then адвизор помечает «думает (xhigh)» и планирует следующий чек, а не «повисал»

### User Story 5: Доменные истины и anti-грабли адвизора зафиксированы в SKILL.md @feature5 (Priority: P2)

**Требование:** [FR-5](FR.md#fr-5-канонический-skillmd-зеркало-доменные-истины)

As a владелец, I want правила адвизора (что есть «пиздёж», что бренд/артикул берётся со страницы и не из slug, что промежуточный 403 ≠ блокер, live vs archived) записаны в канонический скил с зеркалом, чтобы любой новый агент-адвизор вёл себя одинаково.

**Why:** Поведение адвизора в эксперименте было наработано методом проб и ошибок; без фиксации в SKILL.md + parity-реестре оно теряется при смене сессии.

**Independent Test:** `npm run check:skill-health` (или аналог discovery/parity) должен пройти с учётом нового скила; `grep out-session-advisor SKILL.md` показывает блоки «Принципы» и «Доменные истины».

**Acceptance Scenarios:**

Given скил `out-session-advisor` создан в `.claude/skills/` и зеркале `.agents/skills/`
When запускается discovery/parity-чекер скилов
Then спека/парность проходят, зеркала идентичны

Given адвизор читает SKILL.md по триггеру «будь адвизором»
When воркер заявляет «бренд из URL-slug»
Then адвизор помечает как deffect и направляет смотреть страницу после открытия (h1/Бренд/Артикул)

# Часть B — Параллельная безопасность

### User Story 6: Параллельные сессии в одном репо не роняют чужую работу @feature6 (Priority: P1)

**Требование:** [FR-6](FR.md#fr-6-git-гейт-против-add-a-и-чужих-staged-runtime-слой-no-git-add-all-shared-tree)

As a владелец, запускающий несколько параллельных агентных сессий в одном репозитории, I want сессии не затирали файлы и коммиты друг друга, чтобы чужие незакоммиченные изменения не улетали в чужой коммит и не терялись при `git add -A`.

**Why:** Инцидент `12220e5` (2026-06-07): `git add -A` утащил в коммит спеки/tools параллельной сессии; правило `no-git-add-all-shared-tree` покрывает дисциплину, но нет автоматической детекции/предупреждения о пересечении собственных и чужих изменений.

**Independent Test:** BDD-сценарий `@feature6` — симуляция двух сессий: вторая правит не-наш файл, первая коммитит с `git add -A` → гейт детектирует чужие пути и блокирует/предупреждает.

**Acceptance Scenarios:**

Given в рабочем дереве есть чужие незакоммиченные файлы другой сессии
When сессия выполняет `git add -A` / `git add .`
Then инструмент детектирует чужие пути и блокирует команду или предупреждает до коммита

Given сессия коммитит явным перечислением своих путей
When среди них есть файл, который только что изменила другая сессия
Then инструмент помечает конфликт/пересечение и требует подтверждения владельца

### User Story 7: Атомарные локалы и стореджи не дают параллельным апдейтам сломать состояние @feature7 (Priority: P1)

**Требование:** [FR-7](FR.md#fr-7-атомарный-лок-сервис-с-владельцем-и-stale-восстановлением)

As a владелец параллельных сессий, я использую атомарные локалы (`flag:'wx'`) и atomic-сохранение конфигов, чтобы два процесса, пишущие один файл/лок, не приходили к рассинхрону и не коррумпировали состояние.

**Why:** Правила `atomic-update-lock` (лок через О_EXCL, не exists+write) и `atomic-config-save` (temp+move) уже зафиксированы, но не имеют runtime-вердикта «кто держит лок» и нет единой диагностики для адвизора (who-holds-what).

**Independent Test:** BDD-сценарий `@feature7` — два процесса пытаются установить один лок; второй должен получить `<exists>` без порчи первого, stale-лок переживает и разблокируется.

**Acceptance Scenarios:**

Given файл-лок не существует
When процесс A создаёт его через `writeFile(lock, pid, {flag:'wx'})`
Then лок создан атомарно, процесс B при той же попытке получает отказ (EEXIST), а не перезаписывает

Given лок остался после упавшей сессии (stale)
When новый процесс обнаруживает stale-лок
Then он удаляет и пересоздаёт атомарно, логируя факт восстановления

### User Story 8: Несколько репозиториев изолируются по worktree/процессам @feature8 (Priority: P2)

**Требование:** [FR-8](FR.md#fr-8-инвентаризация-сессий-по-нескольким-репо)

As a владелец, работающий в нескольких репо одновременно (sales, presentation-reels, dev-pomogator), I want инструмент видел какие сессии/ворктри/процессы принадлежат каждому репо, чтобы адвизор и владелец могли отличить чужую активность и не принимали её за свою.

**Why:** В live-эксперименте репо делил один `git status` и зомби-Chrome на порту 9333 от другого тула сломал CDP; без карты «сессия → репо → процессы» адвизор не может отделить чужое от своего.

**Independent Test:** BDD-сценарий `@feature8` — инвентаризация процессов/сессий по нескольким заданным репо, категоризация каждого в `<repo>` или `unknown`.

**Acceptance Scenarios:**

Given запущены процессы Claude/агентов в 2+ репо
When запускается инвентаризация `parallel-session-inventory`
Then каждый процесс отнесён к репо по пути/session-id, чужие помечены `unknown/<repo>`, живые vs завершённые

Given session-pilot показывает worktree/session dashboard
When адвизору нужна карта «какие сессии сейчас активны»
Then отдаётся детерминированный список с repo, pid, session-id, временем последней активности

### User Story 9: Адвизор видит владельца/писателя изменений перед тем как править @feature9 (Priority: P2)

**Требование:** [FR-9](FR.md#fr-9-диагностика-кто-писал-файл-single-writer-для-адвизора)

As a адвизор, I want перед правкой файла знать, кто сейчас пишет в этот файл в параллельных сессиях, чтобы не порвать single-writer и не регрессить чужую работу.

**Why:** Правило «один писатель в один файл» нарушалось бы, если адвизор правит файл, который воркер сейчас редактирует по транскрипту; нужен быстрый «кто держит»-запрос.

**Independent Test:** BDD-сценарий `@feature9` — по пути файла вернуть список сессий, чей недавний Edit/Write затрагивает этот файл, с временем последней записи.

**Acceptance Scenarios:**

Given файл покрыт недавними правками двух сессий
When адвизор запрашивает «кто писал <path>»
Then ответ: сессии с временем последнего Edit/Write (по транскриптам), помечая последнего писателя

Given файл правится живой воркер-сессией прямо сейчас
When адвизор собирается его менять
Then адвизор получает предупреждение о конфликте single-writer и не пишет до завершения воркера

### User Story 10: Диагностика и гейты «кто/что/почему» для параллельной работы @feature10 (Priority: P3)

**Требование:** [FR-10](FR.md#fr-10-сводная-диагностика-параллельности-okdirtyconflict)

As a владелец, I want сводную диагностику параллельности (active сессии, локалы, писатели, пересечения), чтобы быстро понимать, что реально происходит, когда две сессии спорят за один файл.

**Why:** Пострашный «неблокирующий» гейт в эксперименте («403 навсегда») был симптомом логики одного писателя/блокера; диагностика должна показывать причинно-следственную связь, а не только факт блокировки.

**Independent Test:** BDD-сценарий `@feature10` — вывод сводки: активные сессии+N, локалы+N, писатели по конфликтным файлам, вердикт по каждому как `ok/dirty/conflict`.

**Acceptance Scenarios:**

Given запущены параллельные сессии с одним конфликтным файлом
When вызывается диагностика параллельности
Then в сводке указаны: каждая сессия (repo/sid/pid), локалы с владельцем, писатели спорного файла, вердикт `ok|dirty|conflict` и причина

Given нет активных чужих сессий
When вызывается диагностика
Then сводка короткая (`0 active, 0 locks, 0 conflicts`) и не спамит
