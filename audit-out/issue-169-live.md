## Сводка

Каждое функциональное требование (FR) должно само объявлять, **какие типы артефактов поставки для него обязательны** — например «реализация», «интеграционный тест», «документация», «миграция», «эксплуатационное доказательство» (operational proof). Типы берутся из закрытого валидированного реестра. Отчёты о статусе спеки тогда честно показывают, каких **заявленных** артефактов не хватает, отдельно от «просто ничего не сделано». Пользовательская возможность: «я вижу не только “FR реализован”, а “FR требует интеграционный тест и миграцию — тест есть, миграции нет”, и вердикт это отражает».

## Проблема сегодня

Сегодня «готовность» FR выводится только из двух сигналов — статуса задач и результатов сценариев, без понятия «какие артефакты требование вообще требовало»:

- `tools/spec-graph/fr-census.ts` — `computeFrCensus()` возвращает `FrCensusVerdict` (`IMPLEMENTED / DONE_UNTESTED / IN_PROGRESS / PLANNED / UNIMPLEMENTED`); `IMPLEMENTED` ставится, когда **все** ссылающиеся задачи `done` И сопоставленные сценарии `PASSED` (`allDone && allVerified`). Никакого измерения «а требовалась ли миграция/документация и есть ли она» нет.
- `tools/spec-graph/types.ts` — `FrNode` несёт `title`, `body`, `frontmatter?` (невалидированный YAML-объект) и `anchors[]`; поля «требуемые типы артефактов» не существует. `frontmatter` — ближайшая полка, но он нетипизирован и ничем не проверяется.
- Класс находок «чего-то не хватает» уже есть в `tools/spec-graph/conformance.ts` как `FindingCode`: `FR_NO_RESEARCH`, `FR_NO_DESIGN`, `FR_NO_STORY` — но это фиксированный, зашитый в код набор, а не данные, объявленные самим требованием.
- Авторская дверь (`tools/spec-mcp-server/tools.ts`, `amend_requirement` / `add_acceptance_criterion`, FR-60d) сегодня принимает только текст и связи FR↔AC; места объявить «этот FR требует документацию + миграцию» нет.

Последствия на реальном рабочем процессе: критичный FR, для которого владельцем задуманы «реализация + интеграционный тест + миграция», формально становится `IMPLEMENTED`, как только закрыты задачи и зелёные сценарии, — даже если миграционный скрипт и пользовательская документация так и не появились. Вердикт врёт «готово», потому что не знает, чего именно требовало требование.

## Пример до/после

**До:** у FR есть `done`-задачи и зелёные BDD-сценарии → `computeFrCensus()` печатает `IMPLEMENTED`, `spec-verdict` говорит «готово». При этом документация и миграция отсутствуют — отчёт этого не видит.

**После:** требование само объявляет спрос:

```yaml
# в секции FR (форма — предмет дизайна; иллюстрация на YAML frontmatter FrNode)
demands:
  - type: implementation
    required: true
  - type: integration-test
    required: true
  - type: documentation
    required: true
  - type: migration
    required: false        # опционально — но если указано, должно быть обоснование
    rationale: "затрагивает схему хранилища v1→v2"
```

Тогда статус-отчёт по FR выглядит так:

```jsonc
{
  "fr": "spec-generator-v4:FR-12",
  "taskVerdict": "IMPLEMENTED",          // как сегодня (задачи+сценарии)
  "delivery": {
    "implementation":  "PRESENT",
    "integration-test":"PRESENT",
    "documentation":   "MISSING",        // заявлен, но отсутствует
    "migration":       "NOT_APPLICABLE (rationale: схема не менялась)"
  },
  "overall": "INCOMPLETE"                 // хотя бы один требуемый артефакт MISSING
}
```

## Предлагаемое поведение

- **Реестр типов артефактов** — закрытый валидированный набор имён (напр. `implementation`, `integration-test`, `documentation`, `migration`, `operational-proof`). Неизвестное имя → явная ошибка при авторстве/импорте, не тихое принятие.
- **Спрос требования** — список записей `{ type, required | optional, rationale? }`; `optional`/`not-applicable` **обязаны** нести обоснование (`rationale`), иначе это дыра, через которую спрос тихо обнуляют.
- **Статус-отчёт** различает: `PRESENT` / `MISSING` / `NOT_APPLICABLE (с обоснованием)` / `WAIVED` — и сворачивает в общий вердикт по правилу «ВСЕ требуемые present = delivered» (AND, не OR — см. правило репо `rollup-completeness-all-not-any`).
- **Наследование / проброс спроса** (forwarded needs): требование может пробросить часть спроса вниз на покрывающие его элементы; семантика проброса детерминирована и документирована (что пробрасывается, как резолвится, что происходит при конфликте).
- «Отсутствует заявленный артефакт» — это находка (по образцу `FR_NO_RESEARCH`/`FR_NO_DESIGN` в `conformance.ts`), видимая и в отчёте, и в двери.

## Область (in / out)

**In:**
- Реестр типов артефактов + валидация имён (fail-loud на неизвестных).
- Поле спроса на FR (и, по решению дизайна, на NFR) с `required/optional/not-applicable` и обязательным `rationale` для опциональных.
- Вывод `PRESENT/MISSING/NOT_APPLICABLE` по каждому заявленному типу на реальном графе/репозитории.
- Находки «заявленный артефакт отсутствует» в conformance/отчёте; сворачивание в общий delivery-вердикт (AND).
- Семантика проброса/наследования спроса (forwarded needs) — детерминированная и покрытая тестами.
- Авторство спроса через дверь (`amend_requirement` и т.п.) + миграция существующих `frontmatter`-данных.

**Out:**
- Переопределение `FrCensusVerdict` (он остаётся измерением «задачи+сценарии»; delivery-спрос — дополнительное измерение рядом).
- Нормализованная модель результата тестов (это #168); здесь мы только **потребляем** факт наличия результата.
- SMT/инварианты (#170), типизированные метаданные вроде safety-класса (#171) — отдельные issue; поле спроса может быть носителем для части #171, но схемы разные.
- UI-отрисовка матрицы (частично пересекается с #167).

## Точки реализации (верифицированные пути; архитектура не финализирована)

- `tools/spec-graph/types.ts`: добавить поле спроса на `FrNode` (рядом с `frontmatter?`/`body`); тип записи спроса как часть схемы графа.
- `tools/spec-graph/fr-census.ts`: расширить `FrCensusRow`/`FrCensusReport` delivery-измерением (существующая логика `allDone && allVerified` не заменяется, а дополняется проверкой заявленных артефактов).
- `tools/spec-graph/conformance.ts`: новые `FindingCode` класса `FR_DEMAND_MISSING` по образцу `FR_NO_RESEARCH/FR_NO_DESIGN/FR_NO_STORY`.
- Вывод наличия артефактов из репозитория/графа: переиспользовать существующие обходы (`coverage.ts` `computeCoverage` FR-32, `traceability.ts`, `project-test-trace.ts` для интеграционных тестов) — не дублировать.
- Дверь: `tools/spec-mcp-server/tools.ts` (`amend_requirement`, возможно новая операция) для авторства спроса через ту же validation-before-write, что `apply_spec_change` (FR-60d).
- `tools/specs-generator/spec-verdict.ts` и `spec-status.ts`: учитывать delivery-измерение в смарт-вердикте (не «структурно valid», а по уликам — см. правило `no-structural-valid`).

## Критерии приёмки

- [ ] Типы артефактов берутся из закрытого реестра; неизвестный тип при авторстве/импорте → явная ошибка (fail-loud), а не тихое принятие.
- [ ] Каждый FR может объявить ноль и более требуемых типов с `rationale`; `optional`/`not-applicable` без `rationale` отвергаются.
- [ ] Статус-отчёт показывает **отсутствующие заявленные** типы отдельно от «нет задач вообще»; FR с зелёными сценариями, но без заявленной документации/миграции НЕ читается как полностью поставленный (AND-свёртка, не OR).
- [ ] Унаследованный/проброшенный спрос (forwarded needs) резолвится детерминированно; поведение при конфликте документировано и покрыто тестом.
- [ ] Реальный артефакт-чек: тест прогоняется против настоящего репозитория/графа и сверяет `PRESENT/MISSING` с независимой проверкой (файл/сценарий действительно существует/отсутствует), а не с рукодельным графом.
- [ ] BDD-сценарии (`@featureN`) на смешанные классы требований (один требует только реализацию, другой — реализацию+тест+миграцию) зелёные в Docker-прогоне (не хостовый cucumber), с проверкой delivery-вердикта по slug-id.
- [ ] Существующие вердикты (`FrCensusVerdict`) не регрессируют на спеках, где спрос не объявлен (поведение «как сегодня»).

## Совместимость / миграция

- FR без поля спроса ведут себя ровно как сегодня (delivery-измерение пустое → общий вердикт определяется задачами/сценариями).
- Существующий невалидированный `frontmatter` на `FrNode` мигрируется в типизированный спрос с явным отчётом (что перенесено, что отвергнуто как неизвестный тип).
- `FrCensusVerdict` и коды conformance не переименовываются; добавляются новые коды и дополнительное измерение отчёта.
- Правило свёртки «ВСЕ требуемые артефакты present» согласуется с существующим правилом репозитория `rollup-completeness-all-not-any` (один `done` среди open ≠ COMPLETE).

## Зависимости / связанные существующие issue

- **#168** (адаптеры тест-результатов) — факт «интеграционный тест существует и прошёл» берётся из нормализованного результата; #169 потребляет этот факт как один из заявленных артефактов.
- **#171** (типизированные метаданные требований) — поле спроса может делить носитель с другими метаданными (safety-класс, метод верификации); схемы согласовать, но это разные данные.
- **#167** (traceability matrix / graph views) — отрисовка «требование → заявленные артефакты → их наличие» естественно ложится в те же представления.
- **#162** (программа закрытия spec-generator-v4) — общий зонтик честности вердикта.

## Prior art

- **OpenFastTrace** (`SpecificationItem.java`, L165-170): https://github.com/itsallcode/openfasttrace/blob/main/api/src/main/java/org/itsallcode/openfasttrace/api/core/SpecificationItem.java#L165-L170 — берём модель «needs / forwarded needs»: каждый элемент спецификации объявляет, какие типы покрытия ему нужны, и покрытие считается удовлетворённым, когда эти объявленные нужды закрыты нижестоящими элементами (включая детерминированный проброс нужд вниз по цепочке).
